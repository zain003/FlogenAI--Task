Full-Stack & Scalable Systems Technical Assessment

Tech Stack

Next.js · NestJS · MongoDB · Socket.IO · Redis · Stripe · TypeScript · Docker

Time Limit

Maximum: 72 Hours

The goal is not to build a polished product. We want to evaluate your ability to write production-quality code and understand real-time systems, Redis, concurrency, payments, databases, security, and scalable backend architecture.

Project: Real-Time Service Marketplace

Build a small marketplace where a Customer creates a service request and Providers can submit offers in real time.

Keep the UI minimal. Engineering quality is the priority.

1. Authentication

Implement:

Provider registration/login

Password hashing

Role-based authorization

Protected REST APIs

Authenticated Socket.IO connections

The backend must enforce permissions.

4. Socket.IO — Mandatory

Socket.IO is a major part of this assessment.

Implement real-time events for:

New Request

When a customer creates a request, connected providers should receive an event.

Example event:

 request:created 

New Offer

When a provider submits an offer, the customer should receive it immediately.

 offer:created 

Offer Accepted

The selected provider should immediately receive:

 offer:accepted 

Other providers should receive an appropriate update indicating that the request is no longer open.

Chat

Implement real-time customer ↔ provider messaging.

Messages must also be persisted in MongoDB.

Example events:

 conversation:join 

 message:send 

 message:new 

Users must not be able to join arbitrary rooms or conversations.

Authorization must be performed server-side.

5. Redis — Mandatory

Redis must actually be integrated into the application.

Do not include Redis only in the architecture diagram.

Socket.IO Redis Adapter

Configure the Socket.IO Redis Adapter so WebSocket events can work across multiple NestJS application instances.

The architecture should support instances communicating through Redis Pub/Sub:

 NestJS Instance A  ·  NestJS Instance B  ·  NestJS Instance C 

A client connected to Instance A must be able to receive an event generated by Instance B.

Redis Usage

Use Redis for at least one additional meaningful use case, such as:

Rate limiting

Caching

Presence

Distributed locking

Temporary state

Be prepared to explain why Redis was appropriate for that use case.

7. Concurrency Challenge — Mandatory

A service request can have many offers, but only one offer can be accepted.

Assume two acceptance requests hit different backend instances at nearly the same time.

Your implementation must prevent both from succeeding.

Do not solve this using frontend state.

Implement a backend/database/distributed solution and explain why it is safe.

Using Redis locking is permitted, but the candidate must understand the limitations and failure scenarios of their implementation.

9. Stripe — Mandatory

Use Stripe Test Mode.

Flow:

 Customer accepts offer → Payment created → Customer pays → Stripe webhook → Backend verifies payment → Database updated 

The payment amount must be determined/validated by the backend.

Stripe Webhook

Implement webhook signature verification.

The application must handle:

Successful payment

Failed payment where applicable

Duplicate webhook delivery

Webhook processing must be idempotent.

A duplicate Stripe event must not create duplicate transactions or incorrectly update the system twice.

Do not store card information.
